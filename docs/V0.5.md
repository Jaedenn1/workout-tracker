# Workout Tracker v0.5

v0.5 moves Workout Tracker from a browser-only utility toward an installable, local-first app with an optional cloud-sync layer.

## What shipped

### PWA / installability

- Web app manifest with standalone display mode.
- Home Screen / install controls in the app.
- iPhone instructions for Safari → Share → Add to Home Screen when iOS does not expose a native install prompt.
- App icon and dark theme metadata.
- Service worker registration and an offline fallback page.
- The workout logger remains local-first: network or cloud failures never block set logging.

### Cloud-sync architecture

The app now includes `/api/sync`, backed by Neon Postgres when `DATABASE_URL` is configured in the deployment environment.

The API stores one JSONB snapshot per sync key containing:

- workout history
- routines
- active routine
- in-progress workout drafts

The database table is created automatically on first successful API use:

```sql
CREATE TABLE IF NOT EXISTS workout_sync (
  sync_key_hash TEXT PRIMARY KEY,
  payload JSONB NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

No separate migration command is required for this v0.5 snapshot model.

### Sync-key model

v0.5 deliberately does not add a public multi-user account system yet. Instead, each personal installation can generate a random 48-character sync key.

- The raw sync key stays on the user's device.
- Requests send it to the server as a Bearer token over HTTPS.
- The server stores only a SHA-256 hash of the key, never the plaintext key.
- Using the same key on another device allows that device to restore the same cloud snapshot.
- Restore requires explicit confirmation before replacing local data.
- After the first successful backup, that device checks for local changes and pushes an updated snapshot about every 20 seconds.

Treat the sync key like a password: anyone who has it can read or replace that cloud snapshot.

## Local-first behavior

Existing v0.2–v0.4 localStorage keys remain the source for immediate workout logging, so existing workout history and routines do not need a destructive migration.

The cloud snapshot mirrors the current local data instead of becoming a hard dependency. If the database is unavailable, the app reports that cloud sync is unavailable while continuing to save workouts locally.

## Database configuration status

The code is designed to build safely even when `DATABASE_URL` is absent. `src/lib/neon.ts` lazily initializes `@neondatabase/serverless` only at request time.

When no database URL is configured, `/api/sync` returns HTTP 503 with `configured: false`. This is intentional and prevents the UI from pretending that a cloud backup exists.

To activate real cross-device sync, provision/connect a Neon Postgres database to the Vercel project so Vercel receives `DATABASE_URL`, then redeploy.

## Future authentication upgrade

The sync-key model is appropriate for this personal/private stage. A later release can replace or supplement it with real account authentication (for example Neon Auth) if the app ever needs multiple users, revocable sessions, email login, or server-enforced user identities.
