# Workout Tracker v0.9 — Apple Watch + Live Activity

v0.9 adds the first real-time Apple Watch workout-control layer while preserving the PWA as the main local-first gym logger.

## Architecture

The PWA, iPhone app, and Watch each have explicit responsibilities:

- **PWA Gym Mode** remains the primary routine editor and local workout draft.
- **Native iPhone app** owns WatchConnectivity and ActivityKit.
- **Apple Watch app** edits the shared active session in real time.
- **Live Activity** mirrors current exercise, set progress, and rest countdown on the Lock Screen and Dynamic Island.

Safari does not have access to WatchConnectivity, so v0.9 uses a versioned local JSON bridge between the PWA and native iPhone app.

## PWA Watch bridge

Route: `/watch`

The page exports the current v0.7 Gym Mode draft into a v0.9 Watch Session JSON document and can import the updated native session afterward.

The import updates matching set IDs in the existing Gym Mode draft. It does not append new sets, which prevents a native round trip from duplicating workout data.

## Watch Session schema

```json
{
  "version": 1,
  "revision": 1,
  "id": "watch-leg-day-...",
  "name": "Leg Day",
  "startedAt": "2026-08-27T17:00:00.000Z",
  "activeExerciseIndex": 0,
  "restEndsAt": null,
  "exercises": [
    {
      "id": "leg-extension",
      "name": "Leg Extension",
      "restSeconds": 90,
      "sets": [
        { "id": "set-1", "weight": 100, "reps": 15, "completed": false }
      ]
    }
  ]
}
```

## Phone ↔ Watch sync

`WorkoutConnectivityStore` uses `WCSession` with three delivery paths:

1. `sendMessage` for immediate updates while both apps are reachable.
2. `updateApplicationContext` for the latest authoritative session snapshot.
3. `transferUserInfo` as a background fallback when the counterpart is not reachable.

Every mutation gets a unique action ID and the session carries a monotonically increasing revision. Re-delivery of an already processed action ID is ignored, and older revisions cannot replace newer state.

This means a repeated WatchConnectivity delivery can mark an existing set complete again, but it cannot append a duplicate set because set identity is stable and the session array is authoritative.

## Apple Watch controls

The watchOS app shows:

- current workout and exercise
- completed/total set count
- current set weight and reps
- ±5 lb controls
- ±1 rep controls
- complete-set button
- next-exercise button
- rest countdown
- Skip rest / +30 seconds
- rest-finished haptic while the Watch app is active

## Live Activity

The iPhone app starts or updates a Live Activity whenever a Watch Session is active.

The Lock Screen and Dynamic Island show:

- workout name
- current exercise
- completed / total set count
- live rest countdown or `GO`

Ending the Watch Session ends the Live Activity.

## CI

GitHub Actions now generates one Xcode project containing three products and compiles both simulator apps:

- `WorkoutTrackerNative` (iPhone + embedded Live Activity extension)
- `WorkoutLiveActivity` (WidgetKit / ActivityKit extension)
- `WorkoutTrackerWatchApp` (watchOS)

No Apple signing certificate is stored in GitHub; CI builds with code signing disabled.

## Physical-device boundary

Simulator compilation proves the Swift, WatchConnectivity, WidgetKit, and ActivityKit targets build together. Actual WatchConnectivity delivery, Dynamic Island presentation, and wrist haptics still require a signed iPhone + paired Apple Watch for end-to-end hardware verification.
